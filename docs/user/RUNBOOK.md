# RUNBOOK — восстановление работы VPN

VPN падает двумя способами: сервис упал, или деградировал исходящий трафик. Второй случай коварнее: сервис «active», клиент «подключён», а интернета нет. Именно под него написан этот runbook. Полный reboot сервера почти никогда не нужен.

## Симптомы и диагностика

| Симптом | Вероятная причина | Проверка по SSH |
|---|---|---|
| Клиент подключён, интернета нет | Деградировал WARP-туннель (ошибки исходящего) | `journalctl -u xray --since '-30m' -o cat \| grep -Ec 'wireguard\|outbound'` |
| Клиент не подключается, сервис `active` | Порт 443 занял другой процесс | `ss -tulpn '( sport = :443 )'` |
| Сервис в статусе `failed` | Xray упал; видно в журнале | `systemctl status xray` |
| После reboot логи пустые | journald без persistence (этот кейс закрыт ролью) | `ls /var/log/journal` |

Счётчик ошибок — главный ориентир. Единицы — шум. Десятки — вот он, сбой.

## Точечный рестарт сервиса

Лечит деградацию исходящего. Перезапускается только Xray; клиенты переподключаются за 10–15 секунд.

1. Подключитесь к серверу по SSH. С телефона — Termux или Termius.
2. Снимите диагностический срез до рестарта (после — строк уже не будет):

   ```bash
   journalctl -u xray --since '-30m' -o cat | grep -E 'wireguard|outbound' | tail -20
   systemctl show xray -p NRestarts,ActiveEnterTimestamp
   ```
3. Перезапустите сервис:

   ```bash
   systemctl restart xray
   ```
4. Проверьте результат: `systemctl is-active xray`, `ss -tulpn '( sport = :443 )'`, затем клиент.
5. Ориентир здоровья: Xray занимает ~15 МБ (`free -m`). Во время деградации он ест десятки-сотни мегабайт на бесполезных переподключениях.

## Полный reboot: когда и почему редко

Рестартовать ОС — крайнее средство. Оно сбрасывает в ноль и то, что чинилось точечно, а volatile-журнал до этого вообще лишал возможности понять причину. В этой роли journal сохраняется на диск, а watchdog перезапускает сервис сам — вручную reboot нужен только если:

- не отвечает и SSH;
- `ss` показывает чужой процесс на :443, который нельзя остановить точечно;
- обновления ядра явно просятся (баннер провайдера) — но это плановое действие, не аварийное.

## Логи и снимки

- Логи Xray и системные — journald на диске: максимум 120 МБ и 3 дня. Caps настраиваются в `config/settings.yml` (`xray_journal_*`).
- `journalctl -u xray` — жизнь сервиса: запуски, ошибки, деградация исходящего.
- `journalctl -t xray-obs -n 80` — «чёрный ящик»: каждые 10 минут слушатели, маршруты, firewall-хвост, память, статус WARP-endpoint. Это то, что не удалось поймать вручную после ребута.
- `journalctl -t xray-watchdog` — авто-рестарты и алерты. Watchdog перезапускает сервис не чаще 3 раз в час; дальше пишет `[ALERT]` и ждёт человека. Алерт — сигнал смотреть руками по шагам выше.
- Без SSH, со своей машины: `xrayvpn service status`, `xrayvpn service restart`, `xrayvpn service logs` (выгружает журнал в файл).

## Механика в двух предложениях

WARP живёт внутри Xray. Когда Cloudflare-пир «протухает», Xray не умеет перезапустить туннель на живую — ошибка сыпется потоком, сервис «жив», но глух. Рестарт сервиса пересоздаёт туннель с нуля.
