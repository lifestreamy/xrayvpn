# RELEASE — релизная политика

Как проект выпускает релизы: версионирование, статусы и порядок проверок перед выпуском. Политика применяется с v0.3.

## Для чего и рамки

Вклад в проект приветствуется (issues и pull requests на GitHub). Сигналы качества выпусков — автоматические прогоны CI (GitHub Actions), эксплуатация на боевом VPS и отчёты пользователей по релизам (issues на GitHub). Лестницы «альфа → бета → стабильный» нет; статус определяется конкретными критериями ниже.

## Версионирование

- Версия — трёхзначная `vX.Y.Z` (начиная с v0.4.0; старые двузначные теги — история, не переименовываются).
- SemVer в фазе 0.x: минор (`v0.3 → v0.4.0`) — существенные изменения, включая ломающие (например, смена дефолта CLI-флага); патч (`v0.4.0 → v0.4.1`) — исправления, удаления experimental-возможностей и небольшие переименования (с записью в CHANGELOG).
- Префикс `v` обязателен во всех тегах.

## Статусы и теги

Каждый релиз фиксируется аннотированным git-тегом по коммиту линии разработки `staging`. Релизных веток не заводят.

Статусы — явным списком:

- Код в `staging` без тега — **не релиз и без статуса**; он может никогда не стать релизом.
- **релиз** — plain-тег `vX.Y.Z`: уверенный выпуск, публикуется обычным GitHub Release и занимает канал «Latest». Ставится только после выполнения критериев выхода ниже.
- **experimental** — опциональный маркер непроверенной сборки: тег `vX.Y.Z_experimental` + GitHub Release с флагом pre-release. Применяется, когда код нужно передать в полевую эксплуатацию, не занимая канал «Latest».

- Суффикс `_stable` упразднён (политика от 2026-09-14): перевода статуса больше нет — релиз сразу выходит plain-тегом, а регресс исправляется следующим патчем `vX.Y.Z+1` (fix-forward).
- Теги `v0.2_release` и `v0.3_experimental` выпущены по прежней политике — история, не переименовываются.

### Критерии выхода релиза (все четыре)

1. На релизном коммите — зелёный полный прогон CI: матрица дистрибутивов ubuntu 22.04 / 24.04 + debian 12, firewall-нога, тесты и линт CLI.
2. CI максимально покрывает клиентские сценарии: python-клиент + bash- и PowerShell-обёртки × раннеры ubuntu / windows / macos; недостающее покрытие достраивается до релиза.
3. Владелец вручную прокликал все сценарии использования на реальном VPS по шпаргалке тестирования (`docs/dev/TEST-LOCAL.md`, `docs/user/TEST-VPS.md`): деплой двумя способами, ротация, юзабилити клиентов (отзывчивость, переводы, понятность текстов), реальная работа VPN.
4. На момент релиза нет открытых известных регрессий и хотфиксов.

Календарная выдержка не является критерием (решение 2026-09-09): деплой либо падает сразу, либо работает; основной риск — в процессе развёртывания и генерации конфигов, его и покрывают проверки выше.

## Порядок выпуска

Релиз выпускается один на версию — после выполнения всего запланированного скоупа версии; промежуточные pre-release на частично готовую работу не выпускаются (решение 2026-09-09).

1. Скоуп версии (волны работ) выполнен в `staging`; каждая волна пушится и проверяется зелёным CI до перехода к следующей.
2. `staging` пушится вручную; на head ждётся зелёный полный прогон GitHub Actions: workflow `molecule` (syntax, матрица дистрибутивов, firewall-нога), workflow `python-client` (тесты и линт CLI) и — на PR к main — smoke-сборка standalone-приложения в workflow `release-binaries` (path-фильтр). При падениях — фиксы отдельными коммитами и перезапуск, до зелёного.
3. Один коммит `docs: finalize vX.Y.Z`: `docs/dev/PLANNED.*`, обе половинки CHANGELOG, штампы `Version` / `Last updated` публичных документов, сводка в README, строка в таблицу статусов ниже и bump версии пакета python-client (`pyproject.toml`, `src/xrayvpn/__init__.py`, `uv.lock`) до версии релиза.
4. Владелец выполняет успешное ручное развёртывание релизного содержимого на реальном VPS — релиз публикуется только после этого.
5. PR из `staging` в `main` мержится методом **Create a merge commit** (web-rebase запрещён — пересоздаёт коммиты, срезает подписи и даты).
6. На merge-node ставится подписанный аннотированный тег `vX.Y.Z` и пушится (руками). Push тега запускает workflow сборки: он собирает standalone-приложения четырёх платформ и dists, считает `SHA256SUMS.txt` и — только для plain-тегов — `latest.json`, и создаёт GitHub-релиз в статусе draft — ассеты не блокируют сам тег: при падении сборочной ноги релиз можно выпустить без них и пересобрать позже перезапуском workflow по тегу.
7. Draft публикуется обычным релизом (канал «Latest»): заголовок — имя тега; тело — соответствующая секция CHANGELOG (при необходимости дописывается вручную). Для тега `vX.Y.Z_experimental` релиз отмечается флагом pre-release и канал «Latest» не занимает. Вложения релиза — только публичные файлы; конфиги с ключами в релиз не попадают.

Тег на непроверенный (без зелёного CI) коммит запрещён политикой.

## CHANGELOG

- Пара файлов в корне: `CHANGELOG.md` (RU) и `CHANGELOG.en.md` (EN); на релиз — секция `## [vX.Y.Z] — YYYY-MM-DD` (Added / Changed / Fixed / Removed) со строкой `Status:`. Авто-bump версий нет.
- Заполняется из сообщений коммитов в момент выпуска; обе половины — одним коммитом, структура зеркальна.

## Релизный коммит

Его правила сводятся к шагу 3 «Порядка выпуска»: `docs/dev/PLANNED.*` (переработка «что дальше» под новую версию), штампы публичных документов, сводка README, обе половинки CHANGELOG. Настоящий документ (`docs/dev/RELEASE.md`) до момента выпуска релиза правится обычными коммитами.

Версия пакета python-client всегда равна версии релиза: finalize-коммит бампит `pyproject.toml` и `src/xrayvpn/__init__.py` (и обновляет `uv.lock`) до `vX.Y.Z`; `xrayvpn --version` обязан совпадать с тегом. Рассинхрон ловит тест `tests/test_smoke.py`.
