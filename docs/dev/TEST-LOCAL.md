# Локальный сквозной тест VPN (molecule → клиент)

> Проверено: 2026-08-21 (после первой зелёной molecule-прогонки, ветка alpha). Обновлено 2026-08-26: molecule использует delegated driver и `xray_runtime: native` — Xray ставится прямо на runner, контейнера нет.

Этот документ описывает ручную сквозную проверку после того, как `molecule test` прошёл зелёным. Цель — убедиться, что трафик от локальной машины через установленный Xray реально выходит наружу через REALITY-туннель.

`molecule test` подтверждает только то, что роль развернулась и артефакты на месте. Реальное рукопожатие с сервером, маршрутизация трафика и DNS через клиент — это отдельный шаг. Он полуавтоматический, потому что клиент запускается на вашей машине, а Xray (после перехода на `xray_runtime: native`) — на том же хосте под управлением systemd.

## Что нужно

- WSL2 с Docker Desktop (либо Docker Engine прямо в WSL-дистрибутиве).
- Утилита `mihomo` (ядро Clash Verge). Скачайте из дистрибутива Clash Verge или с GitHub проекта mihomo.
- `curl` для проверок.
- Свободный TCP 443 на стороне WSL2 (см. §1 ниже).

## Шаг 1. Подготовка

Перед тестом проверьте две вещи.

### 1.1. Порт 443 свободен в WSL2

```bash
sudo ss -lntp | grep ':443 '
```

Если порт занят (часто занимает Docker Desktop proxy или другая служба) — остановите соответствующий процесс либо используйте другой порт в molecule-сценарии.

### 1.2. Clash Verge остановлен

Clash Verge ставит свой TUN-драйвер и прокси. Если он активен одновременно с mihomo из теста, будет конфликт портов и TUN-интерфейсов. Остановите Verge на время теста.

## Шаг 2. Достать клиентский конфиг

После `molecule converge` (delegated driver) клиентский конфиг лежит на runner'е: `/root/vpn-configs/clash_client_0.yaml`. Скопируйте его в рабочую директорию:

```bash
cp /root/vpn-configs/clash_client_0.yaml ./clash_client_0.yaml
```

## Шаг 3. Адаптация конфига для теста

Откройте `clash_client_0.yaml` и замените блок, чтобы клиент не пытался ставить TUN (конфликт с основной системой) и мог ходить в локальную сеть:

| Что | Значение по умолчанию | Для теста |
|---|---|---|
| `proxies[0].server` | `<IP сервера>` | `127.0.0.1` либо WSL2-IP (см. §3.1) |
| `tun.enable` | `true` | `false` |
| `mixed-port` | `7890` | `7899` (любой свободный) |
| `dns.listen` | `0.0.0.0:1053` | `127.0.0.1:1053` |
| правила `IP-CIDR 192.168/10/172.16` | `DIRECT` | `Proxy` (см. §3.2) |

### 3.1. Какой адрес указывать в `server`

Это зависит от того, где живёт Xray.

| Сценарий | Что писать в `server` |
|---|---|
| Xray в том же WSL2, что и вы | `127.0.0.1` |
| Xray в другом WSL2 или на удалённом хосте | адрес этого хоста (`hostname -I`) |
| Запуск вне WSL2 (Docker Desktop напрямую) | IP из `docker network inspect bridge` |

### 3.2. Зачем менять правила для LAN

Конфиг по умолчанию отправляет трафик к `192.168/10/172.16` напрямую (минуя туннель). Это правильно для продакшена — локалка не должна ходить через VPN. Но для LAN-hop-проверки (§5 шаг 7) нам нужно наоборот — пропустить LAN-трафик через туннель. Замените `DIRECT` на `Proxy` только на время теста.

## Шаг 4. Запуск клиента

### 4.1. Валидация конфига

```bash
mihomo -t -d . -f clash_client_0.yaml
```

Если конфиг корректный, увидите `Configuration file ... is valid`. Иначе — ошибка с указанием строки.

### 4.2. Запуск

```bash
mihomo -d . -f clash_client_0.yaml
```

Логи появятся в stdout (или в `mihomo.log`, если включите `log-file` в конфиге). Уровень `info` подойдёт для отладки.

## Шаг 5. Проверки

Выполняйте по порядку. Каждая следующая зависит от предыдущей.

### 5.1. Лог mihomo — нет ошибок TLS/REALITY

Откройте лог mihomo. Не должно быть строк вида `tls: handshake failure` или `reality: ...` с ERROR-уровнем. Если есть — рукопожатие не прошло, дальше идти нет смысла, разбирайтесь.

### 5.2. Лог Xray — успешные подключения

```bash
journalctl -u xray --no-pager -n 30
```

Должны быть строки вида `accepted ... vless ...`. Если их нет — клиент к серверу не достучался.

### 5.3. CONNECT — `generate_204`

```bash
curl -x http://127.0.0.1:7899 https://google.com/generate_204
```

Ожидаемый ответ: пустое тело и HTTP-код `204`. Это проверка, что туннель вообще поднимается и HTTPS через него работает.

### 5.4. EXIT-IP — `ifconfig.io`

```bash
curl -x http://127.0.0.1:7899 https://ifconfig.io
```

Ожидаемый ответ: IP вашего VPS (без WARP) либо IP Cloudflare (с WARP, но WARP в molecule-сценарии выключен). Не домашний IP провайдера — иначе трафик идёт мимо туннеля.

### 5.5. DNS через mihomo

```bash
nslookup google.com 127.0.0.1 -port=1053
```

Ожидаемый ответ: `Address: 198.18.x.x` (fake-IP из mihomo) либо реальный IP `google.com`. Если DNS не резолвится — проверьте, что в конфиге mihomo блок `dns.listen` смотрит на `127.0.0.1:1053`.

### 5.6. LAN TCP через туннель

```bash
curl -x http://127.0.0.1:7899 http://<адрес в локалке>:<порт>
```

Пример: `curl -x http://127.0.0.1:7899 http://192.168.1.1:80`. Должен ответить ваш роутер. Это проверка, что трафик к LAN-хостам тоже идёт через туннель (после правки правил в §3.2).

ICMP через Xray не туннелируется, поэтому `ping` с этой проверкой не работает. Используйте TCP (curl, wget, nc).

## Шаг 6. Завершение

Когда все 7 проверок зелёные, ручной сквозной тест считается пройденным.

Зафиксируйте результат в этом файле:

```
- 2026-08-21 — сквозной тест пройден (molecule + mihomo, WSL2, Ubuntu 22.04).
```

После этого можно коммитить изменения.

## Частые ошибки

| Симптом | Скорее всего |
|---|---|
| `Connection refused` на curl | Порт 7899 занят другим процессом, либо mihomo не стартовал |
| `502 Bad Gateway` | mihomo не может достучаться до Xray (см. §3.1) |
| DNS отвечает, но HTTP не ходит | правила в §3.2 не исправлены, трафик уходит DIRECT |
| Xray journal: `connection refused` от клиента | неправильный `server` в конфиге (см. §3.1) |
